# Decision Router using Laya MCP on Hermes Agent 

The project assumes locally running Kubernetes/Kind Cluster, Openshift/OKD Cluster, Hermes Agent.
The nodejs-oc & nodejs-k8s are projects based upon Openshift & Kubernetes nuances respectively.
Laya is used by Hermes Agent to decide & route deployment to either of them.

A Model Context Protocol (MCP) stdio server for [ConvAI Innovations' Laya](https://github.com/NandhaKishorM/laya) decision models.

The Node.js process owns the MCP protocol and translates tool calls to the official `laya-serve` HTTP API. Laya performs the local model inference; this wrapper does not call a generative LLM or an external decision API.

## Tools

| Tool | Purpose |
| --- | --- |
| `decide` | Answer multiple typed questions in one request: `choice`, `score`, and `noul` |
| `classify` | Select one label and return its probability distribution |
| `score` | Rate text on an ordered scale and return the distribution |
| `check` | Answer a yes/no question and return `P(yes)` / `P(no)` |
| `judge` | Judge Kubernetes/OpenShift intent, risk, and verdict with a confidence gate |
| `route_step` | Let Laya select one immediate Kubernetes/OpenShift workflow step |

All tools are read-only. Laya may download model weights from Hugging Face on the first inference and may take longer while a checkpoint is loading.

## Requirements

- Node.js 20 or newer
- Python 3.10 or newer for the official Laya runtime
- A running `laya-serve` instance, or the `laya[serve]` package if using autostart

Install the Laya HTTP service in a virtual environment:

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install "laya[serve]"
```

For a GPU, install the appropriate PyTorch build for the host before installing Laya. The first request may download several gigabytes of checkpoint data from Hugging Face.

## Run the wrapper

Install and build the Node package:

```bash
npm install
npm run build
```

Start the Laya service in one terminal:

```bash
.venv/bin/laya-serve
```

The default service URL is `http://127.0.0.1:8000`. The wrapper is an MCP stdio server, so do not run it as an interactive command; start it from an MCP client.

For development:

```bash
npm run dev
```

## Configuration

The wrapper reads configuration from the environment. `.env.example` is a template; the Node process does not load `.env` files automatically, so export the variables or set them in the MCP client configuration. See `.env.example` for a complete list.

| Variable | Default | Description |
| --- | --- | --- |
| `LAYA_API_URL` | `http://127.0.0.1:8000` | Base URL of `laya-serve` |
| `LAYA_API_KEY` | unset | Optional bearer token; sent only in the `Authorization` header |
| `LAYA_MODEL` | unset | Optional checkpoint pin: `english`, `multilingual`, or `typed-decisions` |
| `LAYA_CONFIDENCE_THRESHOLD` | `0.8` | Default `answer_confidence` gate for `judge` and `route_step`; per-call values override it |
| `LAYA_CALIBRATION_FILE` | unset | Optional post-hoc calibration JSON generated by `npm run calibrate`; absent/stale entries use `T=1` |
| `LAYA_AUTOSTART` | `0` | Set to `1` to start and supervise a local `laya-serve` child process |
| `LAYA_REQUEST_TIMEOUT_MS` | `300000` | HTTP inference timeout; increase for first-time checkpoint downloads |
| `LAYA_STARTUP_TIMEOUT_MS` | `120000` | Autostart health-check timeout |
| `LAYA_PYTHON` | `python3` | Python executable used with `LAYA_SERVE_MODULE` |
| `LAYA_SERVE_COMMAND` | `laya-serve` | Executable used for autostart |
| `LAYA_SERVE_MODULE` | unset | If set, autostart runs `LAYA_PYTHON -m <module>` |
| `LAYA_SERVE_ARGS` | `[]` | JSON array of extra arguments for the autostart command |
| `LAYA_PRELOAD` | `0` | Passed to the autostarted service; `0` lazy-loads checkpoints |

`LAYA_AUTOSTART=1` is convenient for a local Hermes setup:

```bash
LAYA_AUTOSTART=1 LAYA_API_URL=http://127.0.0.1:8000 node dist/src/index.js
```

Autostart only supports a local `http://` root URL. It does not download or install Python packages; install `laya[serve]` first. If the service is already running, the wrapper reuses it.

## Hermes Agent configuration

Add the built wrapper under `mcp_servers` in `~/.hermes/config.yaml`:

```yaml
mcp_servers:
  laya:
    command: "node"
    args:
      - "/absolute/path/to/decision-router/dist/src/index.js"
    env:
      LAYA_API_URL: "http://127.0.0.1:8000"
      LAYA_AUTOSTART: "1"
      # Use absolute paths so Hermes does not depend on an activated virtualenv.
      LAYA_PYTHON: "/absolute/path/to/decision-router/.venv/bin/python"
      LAYA_SERVE_MODULE: "laya.serve"
      LAYA_DEVICE: "cpu"
      LAYA_PRELOAD: "0"
      LAYA_CONFIDENCE_THRESHOLD: "0.8"
      # LAYA_CALIBRATION_FILE: "/absolute/path/to/laya-calibration.json"
    tools:
      include: [decide, classify, score, check, judge, route_step]
      resources: false
      prompts: false
    timeout: 300
```

Restart Hermes or use `/reload-mcp` after changing the configuration. Hermes discovers the six tools at startup and registers them as MCP tools. The first inference can take longer while Laya downloads or loads a checkpoint, so keep the Hermes timeout at or above the wrapper's request timeout.

If Hermes does not automatically restart a stdio server after a configuration change, restart the Hermes session.

## Tool examples

### Classification

```json
{
  "text": "I was charged twice and need a refund",
  "labels": ["billing", "technical", "other"],
  "instructions": "Which team should handle this request?"
}
```

The result includes the selected `label`, `confidence`, `scores` (the full label distribution), and routing/usage metadata.

### Typed decisions

```json
{
  "state": {
    "subject": "Duplicate charge",
    "body": "I was charged twice this month."
  },
  "questions": {
    "department": {
      "type": "choice",
      "instructions": "Which department should handle this?",
      "criteria": {
        "billing": "Invoices, charges, and refunds",
        "technical": "Bugs and outages",
        "other": "Everything else"
      }
    },
    "urgent": {
      "type": "noul",
      "instructions": "Does the customer need an immediate response?"
    }
  }
}
```

For `score` questions, `criteria` is ordered from the lowest level to the highest level. For `noul` questions, the result is a probability of `true` (the wrapper exposes this as `yes` for `check`).

### Kubernetes and OpenShift workflow decisions

Use `judge` before operational routing. It runs fixed Kubernetes- or OpenShift-specific intent, risk, and verdict questions in one prediction:

```json
{
  "state": {
    "request": "Roll out the reviewed API image to production",
    "namespace": "payments",
    "environment": "production"
  },
  "platform": "kubernetes",
  "threshold": 0.85
}
```

The response includes `intent`, `risk`, `verdict`, per-question probabilities, and a `gate`. The gate uses calibrated `answer_confidence`—the probability assigned to the reported answer—not Laya's entropy-based `confidence` field. The overall judge confidence is the minimum across its three required decisions. A failed gate is advisory evidence to stop and gather context or request human review; it is never authorization to execute a cluster action.

After a successful judge result, use `route_step` to offload the immediate next-step decision to Laya:

```json
{
  "state": {
    "request": "The new OpenShift Route is not serving traffic",
    "project": "storefront"
  },
  "platform": "openshift"
}
```

The built-in presets cover inspection, build, apply, rollout verification, diagnosis, scaling, rollback, and escalation. Platform-specific details such as Projects, quota, BuildConfigs, ImageStreams, SCC, and Routes are part of the OpenShift schema. To use an organization-approved workflow, pass `steps` as a label-to-description object; those labels replace the preset and `escalate` is added automatically:

```json
{
  "state": { "request": "Publish the reviewed service" },
  "platform": "openshift",
  "steps": {
    "inspect_project": "Verify Project, quota, permissions, and current Route state",
    "publish": "Create the approved Route from the reviewed manifest"
  }
}
```

`route_step` returns the selected suggestion in `suggested_step`. It only places that value in `next_step` when the confidence gate passes; otherwise `next_step` is always `escalate`. Both tools are read-only and do not run `kubectl`, `oc`, builds, or mutations.

### Post-hoc temperature calibration

No production calibration values are guessed or shipped. Until labeled held-out data is fitted, calibration metadata reports `neutral` and the wrapper leaves Laya's serialized probabilities at `T=1`.

Create a JSONL file with labeled states. Each `judge` row must provide all three labels:

```json
{"tool":"judge","platform":"kubernetes","state":{"request":"Inspect the Deployment"},"labels":{"intent":"inspect","risk":"none","verdict":"proceed"}}
{"tool":"route_step","platform":"openshift","state":{"request":"Show build failures"},"label":"diagnose"}
```

Then fit one bounded post-hoc temperature multiplier per actual checkpoint, platform, tool, and question:

```bash
npm run calibrate -- \
  --input calibration.jsonl \
  --output laya-calibration.json \
  --min-examples 20
```

Set `LAYA_CALIBRATION_FILE` to the generated file and restart the wrapper. Schema fingerprints prevent an old fit from being applied after a question definition changes; the response marks such entries `stale` and uses `T=1`.

`laya-serve` returns rounded probabilities rather than raw logits. Applying temperature to those probabilities is therefore a post-hoc calibration of the serialized Router prediction, not a refit of the checkpoint weights. Validate the threshold and calibration on your own held-out workload, especially across option counts and languages. Confidence is evidence for automation policy, not proof that a decision is correct.

### Platform routing guidance

The [platform routing guidance](docs/platform-routing-guidance.md) defines the judge-before-route workflow, input and output contracts, safety controls, and calibration behavior for Kubernetes and OpenShift operations.

### Model selection

The server can route requests using Laya's language/script detection by leaving `LAYA_MODEL` unset. To pin one checkpoint for all calls, use:

```bash
LAYA_MODEL=multilingual
```

The optional `model` argument on each tool overrides the environment setting for that call. Valid values are `english`, `multilingual`, and `typed-decisions`.

## Privacy and security

- With the default local URL, state and questions stay on the machine running `laya-serve`.
- The wrapper never logs request bodies, ticket text, or email contents.
- API keys are read from the environment and are never accepted as MCP tool arguments.
- Tool inputs are bounded and validated before being sent to Laya.
- A configured remote `LAYA_API_URL` changes the privacy boundary; only use a service you trust.

```bash
npm test
```

`npm test` type-checks and rebuilds the project, then starts the compiled MCP server with autostart disabled, waits for its readiness message, and verifies clean shutdown. It does not download model weights or invoke `laya-serve`. Individual checks are also available:

